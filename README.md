# Anmore Social

A quiet, photo-friendly community bulletin. The community feed comes first; upcoming events are secondary. Readers need no account. Static files are served by GitHub Pages at `anmore.social`.

## The trust contract

- **Positive content is selected upstream.** Sources filter before publishing to the relay. This reader has no sentiment classifier, positivity scores, editorial approvals, or moderation queues. Newest is default. The later owner-authorized **optional Top zapped** control sorts only loaded posts by verified community Lightning amounts; it is not a positivity score or personalized/hidden ranking.
- **Content relay only:** posts, profiles, deletions and calendar events come exclusively from `wss://relay.anmore.me`. The sole explicit exception is a **receipt-only** cross-reference on hardcoded `wss://relay.primal.net`: kind 9735, approved issuer/recipient, and exact already-verified visible post IDs. No public-relay content/profile fallback or federation. Metadata, NIP-05, event tags and signed request notification relays never add network destinations.
- **Dynamic author eligibility:** every author must have a valid, signed kind-0 profile claiming an exact `username@trailscoffee.com` NIP-05. Any NIP-05-valid lowercase username (`a-z`, digits, `_`, `.`, `-`) is eligible; there is no hardcoded name/public-key list.
- Author admission fetches **only** `https://trailscoffee.com/.well-known/nostr.json?name=EXACT_USERNAME`, rejects redirects, omits credentials, and requires `names[EXACT_USERNAME]` to equal that profile's lowercase hex public key. Community-recipient discovery separately reads the whole canonical directory with a 128-name ceiling and latest signed profiles in batches of 16. Suffix/lookalike domains, whitespace, mixed-case identifiers, mismatched keys, malformed JSON and network failures do not grant admission. NIP-05 is a domain association, not a guarantee of a post's accuracy.
- Every event is shape-checked, hashed and Schnorr-signature verified using the canonical NIP-01 fields. Relay extras such as `indexed_at` are excluded; a relay's verification cache flag is never trusted. Malformed events, invalid signatures and timestamps later than the reader's current clock are rejected, with no future-clock tolerance. The reader's clock therefore matters.
- Main feed: kinds 1 and 20, newest **signed `created_at`** first by default, lexical event-ID tie-break, ID deduplication. Optional Top zapped sorts verified millisatoshi totals descending, then newest/ID. Its scope is visibly **among loaded posts**, never global Top. No personalization, likes, replies, follows, account/key storage, or other engagement counters. Newest and Top zapped are side-by-side buttons. Selecting Top explicitly scans up to six earlier relay pages (at most 600 admitted page entries per action), rechecks author/deletion authority and receipts, then sorts the expanded snapshot. Refresh in Top repeats the bounded scan. The chronological pagination cursor is independent of amount order. Coverage always says loaded posts; Load more can widen it when a budget is reached. There is no infinite scroll or background content polling.
- **Top timeframe controls:** All time is initially selected within Top; This week starts Monday 00:00 and This month starts the 1st 00:00 in America/Vancouver. The selected period ranks and displays verified sats received during that calendar window, by signed receipt `created_at`, not post creation time. Older posts can therefore win a current window. Calendar starts are inclusive, ends exclusive; future receipts are rejected. All receipts are verified and payment conflicts resolved before filtering; identical invoice reissues conservatively use the earliest verified receipt time. Missing/partial sources retain unavailable/provisional labels. Switching periods does not request invoices or additional relays. Newest hides the controls and uses all-time card amounts.
- **Source retention:** Load more and entering Top recheck previously retained post IDs against Anmore in sequential batches of at most 100 IDs (at most 12 for the session ceiling), including when the previous snapshot reached the end of history. A completed exact read omitting an ID evicts that retained post, even if an earlier overlapping page or Primal receipt still survives. Failed checks clear the displayed snapshot and show an error; they are not treated as successful empty reads. Refresh rebuilds from current source pages. No author-signed deletion is fabricated.
- Calendar: latest addressable revisions of kinds 31922/31923, ordered by upcoming start time and shown in Pacific Time. Four upcoming entries from the latest bounded calendar snapshot are shown, not a claim of an exhaustive calendar. All-day dates are interpreted as calendar dates, not converted through UTC midnight. Calendar identity admission is identical to feed admission.
- **Deletion:** valid same-author NIP-09 kind-5 `e` references hide the exact event; `a` references hide matching addressable revisions at or before the deletion timestamp. Foreign-author and forged requests have no authority. A newer addressable revision may legitimately appear after an `a` deletion. The latest revision is selected _before_ deletion application, so older revisions cannot reappear. Deletion history is re-read on each page/refresh and retained for the in-memory reading session. No content is cached across reloads.

## Per-post community Lightning zaps

All sats go to the community group, **not the author**, at the exact owner-supplied address `coffeeloverc2c2cd@pay.trailscoffee.com`. There is **no generic donation QR/address handoff**. The address and technical post details are informational inside a collapsed disclosure in the post-specific dialog. An explicit amount/request action rechecks the current signed post, author NIP-05/deletions, community recipient profile/directory, and the fixed HTTPS pay endpoint. It signs one NIP-57 request with a fresh anonymous in-memory key, clears that key buffer, serializes once, and requests an invoice from the exact approved callback. No user identity, key persistence, wallet access, payment sending, or Cashu operations are used.

Only a signature-verified, mainnet whole-satoshi BOLT11 with exact request hash, amount, and fresh nonexpired timing is exposed as a local QR/Lightning wallet handoff. Invoice creation is not payment. One callback attempt per post per page session (maximum 32), no automatic retry; reopening reuses the same invoice while valid. Refresh invalidates the dialog. Expired or ambiguous attempts are not silently replaced; users are told to check their wallet. The client has no payment-status/custody authority. The compact dialog asks for sats with **Get invoice**, then hides the amount form and prioritizes **Copy invoice** (the exact raw BOLT11). **Open wallet** is only a generic `lightning:` handoff, not a verified Trails-specific launcher. The copy confirmation suggests pasting in Trails Wallet; no unique Trails wallet scheme or iOS URL handler is claimed. QR is behind **Show QR**, raw text appears only in a manual-copy fallback after clipboard denial, and neither payment nor wallet navigation starts automatically.

Totals count only verified kind-9735 receipts from the endpoint's approved **receipt issuer**, with a separately resolved community **recipient**, signed embedded request, exact post/recipient, invoice description hash over the original description bytes and invoice amount. NIP-57 makes request `lnurl` optional; if supplied it must exactly match the community endpoint, with duplicate/mismatched tags rejected. Notification relay lists are not authority and are never followed. Claimed receipt amount tags are not used. Payment hashes deduplicate across event IDs; conflicting reuse contributes zero. Sender NIP-05 is not required. Counts are provider-attested receipts, not independent cryptographic proof of Lightning settlement. A bounded snapshot can omit/withhold receipts; zero verified sats does not prove no payments. Both fixed relay reads run concurrently with independent four-second receipt deadlines. One healthy source survives the other failing: positive amounts show **N sats · provisional**, missing totals show **—**, with an explicit partial receipt-check note that totals/order may change as receipts become available. These observed snapshots can decrease as well as increase: an earlier verified duplicate can move a payment outside the selected period, and a conflicting payment binding excludes it entirely. Both failures show unavailable, never verified zero. Each source receives one kind-9735 filter containing at most 1,200 exact visible post IDs, limit 1,000; a source reaching that ceiling is discarded as truncated. Event-ID merging retains in-memory source provenance, then payment-hash deduplication prevents cross-relay double counting. Content renders before receipt reads finish. NIP-61 nutzaps are explicitly unavailable, not mixed into Lightning totals.

**Read-only paid-receipt reconciliation passed; release remains gated on independent review:** see `RECEIPT_READINESS.md` for three actual verified receipts (50, 42 and 21 sats), live browser pagination and exact source boundary. Historical unpaid invoice/QR evidence: see `ZAP_READINESS.md`. Two earlier noncanonical requests failed exact hash binding and remain recorded as failures. The frontend now constructs the producer's Nostr field order before sending (never normalizes an invoice hash). One subsequent bounded unpaid 21-sat request passed exact raw-request SHA-256, amount, signature and timing checks; its actual dialog QR independently decoded at 320/390/768/1440 CSS pixels. No payment or receipt publication was attempted. Unpaid invoice/QR evidence is private local evidence, not proof of settlement or receipt delivery.

## Safe rendering

Untrusted text is built with DOM text nodes, never HTML interpolation. HTTPS links are explicit new-tab links with `noopener noreferrer`. Credentials, local/IP hosts, non-HTTPS URLs and executable schemes are not admitted. Up to four HTTPS images per post are lazy-loaded with no referrer; unavailable images become original-image links. Photos are not cropped. External media hosts still receive the reader's IP; source navigation leaves the site. No analytics or browser identity storage is used. Public sources and original source links remain in the text; each card also exposes its relay, author key, event ID, signature and timestamp.

Relay disconnection, declined requests, timeouts, oversize responses and identity-endpoint failures are visible. Failed relay/deletion checks fail closed rather than presenting unchecked content as current. Offline snapshots are labelled as such; an explicit retry while offline clears the feed. No demo posts are shipped in the runtime, and no content is published by this application.

The old identity manager, native composer, calendar grid, World Cup data, and fallback relays remain removed.

## Optional installation and offline boundary

The owner explicitly authorized restoring installable PWA support. This supersedes the earlier **worker-retirement product decision**, not its no-content-caching security invariant. `sw.js` stays at its existing root URL so old registrations can upgrade. New visits register it with `updateViaCache: "none"`; it no longer unregisters itself. See `PWA_READINESS.md` for exact local evidence and remaining physical-device/release checks.

Install help is always available in the footer (including without JavaScript), with device-aware enhanced instructions and a native install button only after the browser supplies `beforeinstallprompt`. Only an explicit button gesture uses that single-use event. There is no first-load modal or automatic native prompt. A compact, non-overlay invitation appears **at the end of the reading flow**, only after a trusted feed/calendar interaction. Dismissing it or receiving a native install result sets a seven-day local cooldown; denied storage falls back to memory. The sole optional preference is `anmore-install-dismissed-at`, a timestamp with no identity, content, engagement history, analytics or network transmission. It is written only after dismissal or an install outcome, never merely for visiting/reading. Standalone mode and `appinstalled` suppress installation prompts. Installation is optional and browser-dependent.

The worker persists **only `offline.html` and `offline.css`** in `anmore-social-offline-v1`. Root/index GET navigations (no query, or the exact old `?source=pwa` launch query) are network-first with `cache: "no-store"`; transport failure returns the dedicated, honest offline landing page. No app shell, posts, calendar, profiles, deletions, receipts, invoices, payment responses, wallet actions, external media, manifest or icons are runtime-cached. Non-landing paths/queries and all non-GET requests bypass the worker; payment/wallet endpoints and external origins are never intercepted. The offline document has no script or zap controls. Browser-managed ordinary HTTP caching is separate from this Cache Storage policy.

Updates wait by default: there is no install-time `skipWaiting`, forced reload, or automatic invoice-session reset. The update notice requires an explicit finished-with-tips/saved-invoice acknowledgement before **Update and reload**; an open zap dialog blocks activation. Only that tab arms a controller-change reload. Other tabs adopt the narrow navigation worker without reloading their invoice sessions. Closing every controlled tab also permits the browser’s normal waiting-worker activation. Activation removes only this product’s obsolete `anmore-social-pwa-*` and `anmore-social-offline-*` caches, preserving the current offline cache and unrelated caches. Clients still controlled by the legacy app-shell worker need an online visit and explicit update (or all tabs closed); until activation, the old worker’s policy still applies. A completed retirement worker may leave no registration; a new online visit registers the successor normally.

The app icons now use the site’s mountain mark rather than the legacy Trails Coffee wordmark. `icons/anmore.svg` is the self-contained source; `npm run icons:pwa` regenerates the PNG variants with local Chromium. Dedicated opaque maskable artwork is pixel-tested inside the central 80%-diameter safe circle. Orientation is not locked; manifest theme matches the page.

## Local development and verification

Node 24 was used. No framework or runtime CDN dependency is required: `app.js` bundles the pinned verifier/signing primitives, invoice reader and QR encoder. New local work must rebuild the bundle before review.

```sh
npm ci
npm test
npm run build
python3 -m http.server 4173 --bind 127.0.0.1
# In another terminal:
npm run qa
QA_URL=http://127.0.0.1:4173 node tests/receipt-live-qa.js
```

Browser QA uses Playwright with `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`; set `CHROME_PATH` for another installed Chromium path. Set `QA_URL` to a separate local port when 4173 belongs to another worktree. Fixture QA is explicitly synthetic and includes an intercepted relay, invented identities and a generated landscape image. It tests 1440/768/390/320 CSS-pixel layouts, chronological pagination, malicious content, provenance, dynamic identity, no browser storage, deletion across pagination/reload, failed identity resolution, key mismatch, relay refusal, empty and offline states. Axe checks WCAG A/AA rules. The Top-button suite additionally exercises an older 1,250-sat winner without manual pagination, a fifth-page winner, six-page bounds, deletion of the highest amount, failure recovery, pressed state, keyboard selection and side-by-side 44px controls. Dialog fixtures verify exact raw-invoice copying, optional QR pixel decoding, clipboard fallback, and all primary actions visible at 320/390 × 480. Live QA makes real read-only Anmore content and Primal receipt requests plus actual HTTPS NIP-05/recipient endpoint reads, captures separate `qa/live-*` evidence, and never publishes. Screenshots and JSON evidence stay in ignored `qa/`, not production content.

Limits are deliberate: 12 raw posts per first Newest page, six content queries/600 admitted page entries per Top action, inclusive timestamp cursors with growing boundary windows, at most 600 boundary records, 60 initial calendar records, batches of 20 authors/address lookups, four simultaneous identity HTTPS checks, a 500-deletion response ceiling, and a 1,200-item session safety ceiling. Safety-limit/timeout states stop visibly rather than silently switching relays or skipping tied timestamps. Relay history can be incomplete or withheld; no single-relay client can prove global deletion or discover records the relay does not serve. A snapshot may become outdated until the next explicit refresh.

## Release boundary

This isolated candidate is local and frozen for independent review. No push, merge or deployment was performed. See `PRODUCTION_READINESS.md` and `qa/production-baseline.json` for the verified GitHub Pages mapping, rollback baseline, test evidence and remaining release gates. The separate, narrowly authorized disposable-event live deletion probe is owned by the parent release process, not this read-only browser.

Protocol references: official `nostr-protocol/nips` repository, NIP-01, NIP-05, NIP-09 and NIP-52, read directly from their current source during implementation.
